@CLAUDE.md

You are an expert in INAV firmware target configuration with deep knowledge of STM32 microcontrollers, timer/DMA resource management, pin mapping, and flash optimization.

## Your Responsibilities

1. **Analyze target configurations** - Read and compare target.h/target.c files
2. **Diagnose flash overflow** - Identify root causes and suggest optimizations

See its own docstring and the lessons-learned entry below for the two "dead output" causes it distinguishes. **Known limitation (detection fixed 2026-08-21, isolation still manual):** `parse_target_c()` still flattens `#if`/`#else`/`#ifdef` blocks into one array, which can silently corrupt position numbers (not just cause an obvious self-collision) on targets with conditional compilation in `timerHardware[]` -- but it is now preprocessor-aware: any `DEF_TIM` line found inside a `#if`/`#ifdef`/`#ifndef` gets `entry.conditional_expr` set, and `has_conditional_tim(entries)` reports whether any parsed entry is conditional. `run_target()`'s CLI output and `classify_collisions.py`'s batch sweep (see its entry below) both check this and report the target as N/A instead of trusting the flattened data. Actually resolving one of these targets still needs each variant isolated by hand -- see `make_pwm_shadow.sh` below. **`USE_DSHOT_DMAR` (burst-mode DMA) aware, and FAMILY-aware:** on a target with `USE_DSHOT_DMAR`, a DMA stream is claimed once per *physical timer* (`tch->timCtx->dmaBurstRef`, shared across all 4 channels of one timer), not per channel -- but which channel's own `dmaGetByTag()`/ownership check actually runs differs by backend, confirmed by direct source comparison: on **F4** (`timer_impl_stdperiph.c`), the check sits INSIDE `if (!dmaBurstRef)`, so once a timer has a winning channel every LATER channel of that SAME timer free-rides without ever consulting its own dmavar at all; on **F7/H7** (`timer_impl_hal.c`, a shared backend -- see the lessons-learned entry on that), the check is UNCONDITIONAL, so every channel -- including a later channel of an already-locked timer -- independently attempts its own claim. `resolve_dmar_cascade()` (in the script) replays this family-aware cascade ONCE and is the single authoritative source reused by all three DMAR-sensitive hazards: `SILENT_DEAD_MOTOR` (a NONE-resolving channel is only safe on F4 if it's genuinely riding an already-succeeded timer; F7/H7 never gets a free pass, confirmed by real H7 `TIM4_CH4` needing an explicit `DMA_REQUEST_TIM4_UP` workaround to pass this same unconditional gate), `DMA_STREAM_COLLISION` for a mixed motor+non-motor group (e.g. LED strip, which never goes through the burst path) which now groups by each motor channel's cascade-resolved *effective* stream rather than its raw per-channel value, and `BURST_STREAM_COLLISION` for a genuine cross-timer (or, degenerate, same-timer-duplicate-dmavar) hazard. See the module docstring's `resolve_dmar_cascade()` section for the full derivation. **`SHARED_TIMER_DMA_REQUEST` is now SOLO-aware (fixed 2026-08-21):** `is_shared_multichannel_request()` used to flag any dmavar resolving to an F4-style combined CH1/CH2/CH3 request line purely off the static header table -- whether a DIFFERENT channel's OWN option list also lists that tuple -- with no check on whether that other channel is actually declared/driven in this specific target (the SOLO false positive: a lone user of the combined line is fine, since nothing else can ever trigger it). It now takes a per-call `active_siblings` set (which channel tokens on that timer are genuinely driven this motorCount, precomputed once per `simulate()` call, de-N'd so `CH2N` counts as `CH2`) and only flags when a sibling from the same combined group is actually in it. A full tree sweep found 29 targets with a genuine remaining hit (SPURIOUS TRIGGERS, real), down from 62 before the fix -- see the lessons-learned entry below and `investigate-shared-tim-dma-request-lines/phase1-findings.md`'s Phase 2 step 5 writeup. **Correction (2026-08-20):** an earlier version of this script applied the F4 free-ride shortcut universally to F7 targets too; fixing that surfaced a REAL, previously-invisible `TIM3_CH2`/`TIM2_CH1` hazard (both resolve to DMA1 Stream5 on different channel selectors) on 5 F7 `USE_DSHOT_DMAR` targets -- **`NEXUSX` and `VANTAC_RF007` are genuine CERTAIN hazards**, not the false positives an earlier pass of this investigation concluded, and `AOCODARCF7MINI`, `FLYDRAGONPRO`, `TMOTORVELOXF7V2` gained a new NOTICE-level instance of the same pattern. `FOXEERF405V2`, `RADIOLINKF405`, `SKYSTARSF405V2`, `TUNERCF405` (all F4) remain confirmed false positives -- the free-ride model is correct for that family. See `claude/projects/active/investigate-shared-tim-dma-request-lines/phase1-findings.md`'s Phase 2 step 2 addendum for the full worked comparison.

Verifies every candidate against the full `simulate_pwm_roles.py` hazard sweep (every `SHARED_TIMER_DMA_REQUEST` hit must clear, no new `DMA_STREAM_COLLISION`/`SILENT_DEAD_MOTOR` may appear) before accepting it. - `claude/agents/target-developer/scripts/classify_collisions.py` - Companion to `simulate_pwm_roles.py`: sweeps a list of F4/F7/AT32 targets across motor counts and classifies each `DMA_STREAM_COLLISION` (and, on `USE_DSHOT_DMAR` targets, `BURST_STREAM_COLLISION` -- see that script's entry above) hazard as CERTAIN or NOTICE. Severity is about the *loser*, not the group: motors claim DMA in strict position order (`pwm_mapping.c:pwmInitMotors`) and the first (lowest-position) claimant always wins, so CERTAIN requires the second-lowest position in the group to be < 4 -- an S1-S4 output actually going dead -- not just any member of the group being < 4. A motor-vs-motor pair where a low position "wins" against a higher one is NOT a hazard for the low side. **A third, separate output category, `LED_COLLISION`** (added 2026-08-21, see the lesson below) reports every MOTOR-vs-LED_STRIP `DMA_STREAM_COLLISION`/`BURST_STREAM_COLLISION` -- severity there is always deterministic (motors init before `ledStripInit()` in `fc_init.c`, so the motor side always wins and the LED strip silently just doesn't light; never flight-critical, so there's no CERTAIN/NOTICE split to make). **A fourth output category, `=== N/A ===`** (added 2026-08-21) lists every target `has_conditional_tim()` flags before it's ever passed to `classify()`/`led_collisions()` -- these targets are skipped from CERTAIN/NOTICE/LED_COLLISION entirely rather than risking a same-(tim,ch) self-collision false positive or, worse, a real hazard masked behind a clean `#ifdef` branch (the `MAMBAF405US` failure mode -- see the lesson below). A full sweep with this fix found 15 N/A targets, 6 more than the by-hand `#if`-grep pass had found before it. Usage: `python3 classify_collisions.py <inav_root> <targets_file>`. Origin and worked example: `claude/projects/active/investigate-shared-tim-dma-request-lines/phase1-findings.md`.
- `claude/agents/target-developer/scripts/check_timer_pin_af.py` - Validates every `DEF_TIM(tim, ch, pin, ...)` triple in target.c against the indexed datasheet AF table (`claude/developer/docs/targets/<mcu>/alternate-functions.tsv`, loaded via the shared `af_tables.py`). **This is the only check for a bug class the compiler cannot catch on STM32F4**: `timer_def_stm32f4xx.h:25` builds the AF number from the TIMER NAME alone (`GPIO_AF_ ## tim`) with no per-pin table, so a wrong triple compiles cleanly and just leaves the pad silently dead. F7/H7/AT32 have per-pin `DEF_TIM_AF__P<pin>__TCH_<TIM>_<CH>` tables so the same mistake is a build error there (findings are still reported, labelled as compile-time-caught). Three finding kinds: `N_MISMATCH` (pin carries `TIMn_CHmN` but target declares `TIMn_CHm`, or vice versa -- the wrong output-enable bit gets set, DMA analysis looks perfectly healthy while the pad never drives), `WRONG_CHANNEL` (right timer, wrong channel -- AF mux is right by luck since channels of one timer share an AF number), `TIMER_NOT_ON_PIN`. First full-tree run found 9 real, previously-undocumented instances across 90 F405 targets -- see the lessons entry below. Wired into `run_target_checks.py` as check 8.
- `claude/agents/target-developer/scripts/find_dead_motor_fix.py` - The `SILENT_DEAD_MOTOR` counterpart to `find_shared_dma_fix.py`: searches **pin remaps** (a different timer/channel on the SAME physical pad), which is outside `find_shared_dma_fix.py`'s dmavar-only search space entirely. Necessary because `SILENT_DEAD_MOTOR` means the (timer,channel) has NO DMA option list at all (TIM9/10/11/12 and TIM4_CH4 are all `NONE` on F405), so no dmavar value can ever help -- but most pins reach several timers, and the alternates usually DO have DMA. Every candidate must pass three hard rules: datasheet-confirmed pin/timer routing (via `af_tables.py`), no `(timer, de-N'd channel)` duplicate with an existing entry, and no new/earlier-biting hazard anywhere in the motorCount sweep. Also runs a **co-fix pass**: if a remap is blocked only because a healthy unrelated entry is holding the DMA stream it needs, it tries that entry's alternate dmavars too (this is what flips CLRACINGF4AIR V2/V3 and MATEKF405SE from "no safe remap" to fixable). `--min-position`/`--max-position` filter by bucket position (default 0..3, the basic-quad range). Reports only; never edits target.c.
- `claude/agents/target-developer/scripts/af_tables.py` - Shared loader for the datasheet AF TSVs plus target->MCU detection (`MCU_TO_INDEX`) and the firmware-side `DEF_TIM_AF__*` table reader. - `claude/agents/target-developer/scripts/check_pin_conflicts.py` - Flags a single physical pin assigned to more than one peripheral macro in target.h. Common benign case: two alternate chip variants sharing one CS pin.

## Workflow

When helping with a target problem, follow this systematic approach:

### Step 1: Understand the Issue
Confirm you have what's listed under Required Context above; ask for whichever the caller didn't provide.

### Step 2: Run the Automated Checks
- `run_target_checks.py <inav_root> --target NAME` (see Core Capabilities #1) -- replaces the manual grep/comparison work in Steps 3-4 below for the bug classes it covers
- Read relevant sections from docs/development/ for anything it doesn't cover
- Reference conversion guide for new targets

### Step 3: Search Git History
Find similar problems and solutions:
```bash
# Search for specific issues
git log --all --grep="flash overflow" -- "src/main/target/"
git log --all --grep="gyro not detected" -- "src/main/target/"
git log --all --grep="DMA conflict" -- "src/main/target/"

# Search for specific target changes
git log --all -- "src/main/target/MATEKF722/"

# Search for similar fixes
git log --all --grep="F405.*flash" -- "src/main/target/"
```

### Step 4: Compare With Working Targets
Use grep to find similar configurations:
```bash
# Find similar MCU targets
grep -r "STM32F405" src/main/target/*/target.h

# Find flash optimization patterns
grep -r "USE_DSHOT" src/main/target/*/target.h

# Check timer definitions
grep -r "DEF_TIM.*MOTOR" src/main/target/*/target.c
```

### Step 5: Provide Actionable Fixes
- Show exact code changes needed in target.h or target.c
- Explain why the fix works (hardware reason, DMA conflict, etc.)
- Reference commit examples with git hashes
- For builds: "Use inav-builder agent to test: build TARGETNAME"

### Step 6: Validate Solution
Suggest testing steps:
1. Use inav-builder agent to compile
2. Check flash usage percentage
3. Test affected hardware (gyro, motors, etc.)
4. Verify no new DMA conflicts

## Self-Improvement: Lessons Learned

When you discover better ways to diagnose or fix target issues, patterns in git history that are particularly useful, or common mistakes to avoid, add them here.

### Lessons

- **PINIO debugging - high-Z multimeter misleads**: A high-impedance multimeter on an output pin causes voltage to fall very slowly, making a toggling pin appear stuck HIGH. Use a low-impedance load or oscilloscope for reliable readings, or account for slow discharge when interpreting multimeter results.
- **BUSDEV_REGISTER_SPI_TAG variable name, DEVHW type, and ALIGN macro must be internally consistent**: e.g. don't name a variable `busdev_icm42688` for `DEVHW_ICM42605` (that constant is correct for both chips, WHO_AM_I auto-detects), and don't reuse another chip's `_ALIGN` macro unless the two chips share identical physical orientation.
- **SoftSerial is unnecessary on targets with 6+ hardware UARTs**: H7/F7 boards have enough hardware UARTs that softserial on an already-used UART TX pin adds no value and wastes flash; it's more defensible on F405 boards for inverted SmartPort telemetry. `check_serial_port_count.py` flags a *dead* `FEATURE_SOFTSERIAL` bit, not this case, since a defined-but-unused softserial pin isn't statically distinguishable from a deliberate design choice.
- **INAV has no bidirectional DSHOT — USE_RPM_FILTER works via ESC_SENSOR over UART, not motor timer topology**: this is a runtime CLI/config choice (which UART is assigned ESC_SENSOR), not visible in target.h, so it isn't checkable statically. Reference: `src/main/flight/rpm_filter.c` line 191, `src/main/sensors/esc_sensor.c`.
- **DMA resolver library (`raytools/dma_resolver/`) is usable directly via Node.js**: add `{"type":"module"}` as its `package.json`, then `node analyze_target.mjs`; use `dmaMapAT32F435` from `dma_maps.js` directly for simple per-target analysis rather than `findSolution()`. AT32F435 with DMAMUX lists all 14 channels as valid for every timer channel — conflict analysis there is just counting total DMA users vs 14 available.
- **Schematic-driven target creation workflow documented**: See `claude/developer/docs/targets/reading-schematics.md` for the full checklist (pin-map extraction from KiCad s-expressions, cross-sheet net matching, H7 DMAMUX vs F4/F7 fixed-DMA analysis, verifying scans against raw schematic text).
- **H7 `dma_maps.js` (resolver tool) can be wrong about individual channel DMA availability**: for ground truth on STM32H7, check `inav/src/main/drivers/timer_def_stm32h7xx.h` directly -- e.g. TIM4_CH4 has no DMAMUX request line on real silicon even though `dma_maps.js` lists options for it (INAV's `USE_DSHOT_DMAR` workaround is a global switch, not a per-channel opt-in; some channels like TIM15_CH2 have no DMAR workaround at all).
- **A commit's "matches board X's convention" claim can be wrong -- verify against X's actual current source, not the message**: AEDROXH7's LED/DMA fix (PR #11629/#11630) claimed to match MATEKH743/MAMBAH743/FOXEERH743/BROTHERHOBBYH743's `dmaopt` convention but used the wrong value, reintroducing a new collision against ADC1 -- see `check_dma_conflicts.py`'s docstring for the full incident.
- **A shared physical timer is claimed atomically for MOTOR or SERVO role at runtime, regardless of per-channel `usage` flags in target.c**: `pwmClaimTimer()` in `src/main/drivers/pwm_mapping.c` force-overwrites `usageFlags` for *every* `timerHardware[]` entry sharing a `TIM_TypeDef*` to match whichever role won that timer, even entries compiled with a different explicit usage (e.g. `TIM_USE_SERVO`-only). If a DSHOT motor and a would-be independent servo share one physical timer (common on F4/F7 boards with fixed AF-limited pins), the servo channel isn't safely "just PWM" -- it's either force-promoted-but-never-driven (dead pad, if it falls outside `idx < motorCount` in array order) or force-promoted-and-driven as an extra DSHOT motor (if motor count is large enough to reach it), never a standalone PWM servo. There is no target.c flag combination that decouples two channels on the same physical timer; the pin-to-timer wiring itself is the only real constraint. Also confirmed while investigating: plain PWM/servo output (`motorConfigPwm`) never touches DMA at all -- only `motorConfigDshot()` calls `timerPWMConfigChannelDMA()` -- so a DEF_TIM DMA tag being *listed* for a channel is irrelevant unless pwm_mapping.c actually resolves that channel into a live DSHOT motor slot.
- **Role-cascade + DMA-collision analysis for motor/servo outputs is now scriptable, not hand-traced**: `claude/agents/target-developer/scripts/simulate_pwm_roles.py` is a faithful Python port of `pwmClaimTimer`/`pwmEnsureEnoughtMotors`/`pwmBuildTimerOutputList` (drivers/pwm_mapping.c) plus per-family DMA-option resolution (F4/F7/AT32 share a dmavar-indexed option-list scheme in timer_def_*.h; H7 uses the flat dmaopt addressing check_dma_conflicts.py already models, imported directly rather than duplicated). Run it with `--sweep` to find, for any target, exactly which motorCount values are DMA-safe, and with `--motor-count N` for a full per-output resolved-role table at one specific count. It distinguishes two previously-conflated "dead output" causes that matter for different reasons: (a) resolved into a bucket (MOTOR/SERVO) but never reached because its position in that bucket is >= the configured motor/servo count -- benign, expected on any board with more pads than configured outputs -- versus (b) genuinely initialized this build but the (timer,channel) has literally no DMA request line on this MCU, which `pwmMotorConfig()` reports as success anyway (drivers/pwm_output.c) -- a silent flight-safety hazard invisible at boot. Built after a session hand-traced this same algorithm for DAKEFPVF405WING and got it wrong twice in one conversation, including presenting an unachievable "S2 solo DSHOT + S3 working servo" recommendation as if verified -- see the script's own docstring for the full derivation and its `--selftest` regression cases. Known static limitation: UART/softserial pin-sharing skips in `checkPwmTimerConflicts()` depend on live runtime serial config, not anything in target.c/target.h, so they are not modeled -- document this if a user reports a UART-shared timer pin behaving unexpectedly.
- **F7 and H7 share one timer/DMA backend file (`timer_impl_hal.c`); F4 and AT32 each have their own**: `cmake/stm32f7.cmake` and `cmake/stm32h7.cmake` both build `drivers/timer_impl_hal.c` — the same HAL/LL-based object code, not just similar logic. F4 builds `drivers/timer_impl_stdperiph.c` (Standard Peripheral Library) and AT32 builds `drivers/timer_impl_stdperiph_at32.c`; these are genuinely separate implementations. A bug found in `timer_impl_hal.c` on one of F7/H7 very likely affects the other too (confirmed on `shrink-ledstrip-dma-buffer`: a DMA peripheral-data-size typo exposed only on H7 by a buffer-element-size change was sitting in code F7 ran identically, just never triggered). Treat "verified on H7" as strong but not certain evidence for F7, and don't assume a fix or bug found on either generalizes to F4/AT32 without checking the corresponding backend file directly — the `#if defined(STM32H7)` branches inside `timer_impl_hal.c` are narrow (DMA request routing field, a `TIM9` clock-source check) and don't cover most of the file.
- **DMA_STREAM_COLLISION severity is about the loser, not the group**: motors claim DMA in strict array-position order (`pwm_mapping.c:pwmInitMotors`), and the *first* (lowest-position) claimant on a shared descriptor always wins and keeps working — every later one silently goes dead. A collision between a low-position and a high-position output is therefore NOT a hazard for the low side; classifying by "does any member of the group sit at position < 4" gets this backwards (a session did exactly this once, reported 59 CERTAIN targets, and had to retract and recompute — correct number was 19). Classify by whether the *second-lowest* position in the group (the best-case loser) is < 4.
- **`parse_target_c()`'s `#if`/`#ifdef` blindness can silently corrupt data, not just cause an obvious self-collision (detection automated 2026-08-21)**: when a `target.c` declares two build variants with genuinely different DEF_TIM entries under `#if`/`#else` (not just a duplicate), flattening both into one array can produce a *plausible-looking but wrong* winner/loser pair (confirmed on `FF_PIKOF4`/`FF_PIKOF4OSD`) — worse than the already-known case where identical labels collapse into an obvious dead giveaway. `parse_target_c()` no longer needs a human to notice this: it now tracks the `#if`/`#ifdef`/`#ifndef`/`#elif`/`#else`/`#endif` stack while scanning and tags every `DEF_TIM` line found inside one with `entry.conditional_expr` (the guarding condition text). `has_conditional_tim(entries)` is `True` if any entry is tagged; `run_target()` and `classify_collisions.py` both check it and report N/A instead of a trusted verdict. Actually resolving a flagged target still needs each variant isolated by hand (see `make_pwm_shadow.sh`) — the fix is detection, not simulation of multiple variants at once. A full re-sweep with the fix found 15 conditional-compilation targets, 6 more than the previous manual `#if`-grep pass (`FF_PIKOF4`, `FOXEERF722V4`, `KAKUTEF4`, `RUSH_BLADE_F7`, `SKYSTARSF405HD`, `SPRACINGF4EVO`) — the manual process itself had been missing real cases, which is exactly the failure mode automating it was meant to close.
- **`USE_DSHOT_DMAR` invalidates naive per-channel DMA-stream-collision analysis for motor-vs-motor groups, in both directions (false positives AND missed real collisions) -- and the correct replacement model is FAMILY-DEPENDENT, not universal**: burst mode claims one DMA stream per *physical timer* (`tch->timCtx->dmaBurstRef`, on a context struct shared by all 4 channels of that timer -- `timer.c` `timerGetTCH()`), not per channel. But WHICH channel's own `dmaGetByTag()`/ownership check actually executes differs by backend, confirmed by direct comparison of `timer_impl_stdperiph.c` (F4) against `timer_impl_hal.c` (F7/H7, a shared backend file -- see the separate lessons entry on that sharing): on **F4**, the check sits INSIDE `if (!tch->timCtx->dmaBurstRef)`, so once ANY earlier channel of a timer has succeeded, every LATER channel of that SAME timer skips the check entirely and free-rides, never touching its own dmavar; on **F7/H7**, the check runs UNCONDITIONALLY before that guard, so every channel -- including a later channel of an already-locked timer -- always makes its own independent claim attempt against its own resolved stream. Three corrections found while building/refining the fix (`claude/projects/active/investigate-shared-tim-dma-request-lines/phase1-findings.md`, Phase 2 step 2 and its 2026-08-20 fix pass): (1) a failed claim does NOT mean "the whole timer is dead" -- `dmaBurstRef` stays unset on failure, so the *next* channel of that same timer (F4) or the *next attempt itself* (F7/H7, which never skipped in the first place) gets its own fully independent retry; (2) a failed claim does NOT abort `pwmInitMotors()`'s loop -- `motorConfigDshot()` returns a non-NULL port regardless of DMA success (only `port->configured` is gated), and `pwmMotorConfig()`'s return value is just `pwmPort != NULL`; (3) **applying the F4 free-ride shortcut universally to F7 targets is itself a bug, not just a simplification** -- an earlier pass of this investigation did exactly that and concluded all 6 originally-flagged `USE_DSHOT_DMAR` targets (`FOXEERF405V2`, `NEXUSX`, `RADIOLINKF405`, `SKYSTARSF405V2`, `TUNERCF405`, `VANTAC_RF007`) were false positives; correcting the model to make F7 always attempt its own claim (matching the unconditional gate in `timer_impl_hal.c`) revealed that **`NEXUSX` and `VANTAC_RF007` (both F7) are genuine CERTAIN `TIM3_CH2`/`TIM2_CH1` collisions** (`D(1,5,3)` vs `D(1,5,5)` -- same DMA1 Stream5, different channel selectors, so both can't really be live at once), while the 4 F4 targets in that original list remain correctly-suppressed false positives (the free-ride model IS correct for F4). The same fix also surfaced a previously-undetected NOTICE-level instance of the identical `TIM3_CH2`/`TIM2_CH1` pattern on 3 more F7 `USE_DSHOT_DMAR` targets not in the original 6 (`AOCODARCF7MINI`, `FLYDRAGONPRO`, `TMOTORVELOXF7V2`). `simulate_pwm_roles.py`'s `resolve_dmar_cascade()` now implements this family-aware cascade as the single source of truth for `SILENT_DEAD_MOTOR`, `DMA_STREAM_COLLISION` (including a DMAR motor channel colliding with a non-motor claimer like LED strip -- grouped by each motor channel's cascade-resolved *effective* stream, not its raw per-channel value, since a free rider's raw value was never actually consulted by real firmware), and `BURST_STREAM_COLLISION`; `classify_collisions.py` treats `BURST_STREAM_COLLISION` identically to `DMA_STREAM_COLLISION` for severity (same "loser position < 4" rule). **H7's separate flat-`dmaopt` model (`check_dma_conflicts.py`) needed no equivalent fix**: real H7 `USE_DSHOT_DMAR` targets assign each channel of a burst timer a genuinely distinct `dmaopt` (confirmed on `AXISFLYINGH743PRO`'s `TIM4` CH1-4: opts 9,10,11,12, not a shared value), so its existing per-channel-value model already matches H7's unconditional-gate reality; its dead-code "same timer + `USE_DSHOT_DMAR` -> always skip" branch rests on an F4-style shared-request-line assumption that has never actually triggered on any real H7 target (verified empirically across all H7 `USE_DSHOT_DMAR` targets) but would be worth revisiting with the same family-aware logic if a future target ever hits it.
- **`classify_collisions.py` could never detect a MOTOR-vs-LED_STRIP collision at all, structurally, until fixed 2026-08-21**: `simulate_pwm_roles.py`'s per-row loop only assigns a `position` for the MOTOR and SERVO buckets; the LED branch leaves it `None`. `classify()`'s `involved` list comprehension filters out any tim_ch whose looked-up position is `None` *before* the `len(involved) < 2` check even runs, so a real motor-vs-LED hazard always collapsed to a 1-element list and silently vanished on every prior run -- not misclassified, invisible. Found by hand on `AIKONF7` (its `TIM3_CH2`/S2 vs `TIM2_CH1`/`TIM_USE_LED` collision fires at every motorCount from 4 up and had zero prior documentation despite `AIKONF7` being on the NOTICE list for an unrelated pair in the same file) during `investigate-shared-tim-dma-request-lines` Phase 2 step 3, then confirmed with a full 189-target universe sweep that found one more previously-invisible case (`FURYF4OSD`). Fixed with a structurally separate `led_collisions()` pass and new `LED_COLLISION` output category -- severity there is always deterministic (motors init before `ledStripInit()` in `fc_init.c`, so the motor side always wins; never flight-critical), so there's no CERTAIN/NOTICE split needed, just detection. See `claude/projects/active/investigate-shared-tim-dma-request-lines/phase1-findings.md`'s "Update 2026-08-21" section for the full writeup and the corrected LED-strip-collision count (6, not 4).
- **A hazard check that only looks at the static DMA-option header table, not at what's actually declared in the specific target, can be structurally unable to tell "possible" from "real" (fixed 2026-08-21, `SHARED_TIMER_DMA_REQUEST`)**: `is_shared_multichannel_request()` flagged any channel using an F4-style combined CH1/CH2/CH3 request line whenever the header table showed a DIFFERENT channel of that timer COULD also use the same tuple -- regardless of whether that other channel was ever declared, let alone driven, in the target actually being checked. That conflated the SOLO pattern (no sibling present at all -- harmless, the line only ever sees this channel's events) with the real SPURIOUS TRIGGERS pattern (a sibling genuinely declared and driven -- its compare events really do leak onto the shared line). Fix: precompute which channel tokens per physical timer are actually driven this `motorCount`/`servoCount` (`simulate()`'s `active_ch_by_tim`, before the per-row loop, since bucket/motor_pos/servo_pos are already fully resolved by then) and require a real intersection with the candidate sibling set, not just table membership. A full tree sweep dropped the flagged-target count from 62 to 29 (this excludes `USE_DSHOT_DMAR`/AT32 targets the check doesn't apply to, and 3 parser-gap targets unrelated to this fix) -- roughly matching the original problem statement's SOLO (73) vs. SPURIOUS TRIGGERS (10) full-tree classification in shape, though not exact count (different sweep methodology). Lesson generalizes: any hazard check phrased as "entry X's chosen option is ALSO one that sibling Y COULD pick" needs a second gate on whether Y is actually present/active in THIS target, not just structurally possible per the header/table data -- table membership answers "is this combined hardware group," not "is anyone else in it right now."
- **A self-test that reads a real target directory off disk is fragile to that target being renamed/restructured upstream, and the failure mode is silent regression, not a loud one**: `simulate_pwm_roles.py --selftest`'s `entries2` used to `parse_target_c(target_c_path.read_text())` against the real, live `DAKEFPVF405WING/target.c` -- when that target directory was superseded upstream by a differently-laid-out `DAKEFPVF405`, `--selftest` started raising `FileNotFoundError` and aborting BEFORE running roughly half the suite (everything after that line, including the `SHARED_TIMER_DMA_REQUEST` regression check above), and nobody would necessarily notice a crash-early failure is silently skipping checks rather than confirming them. Found and fixed while verifying the `SHARED_TIMER_DMA_REQUEST` fix needed working regression coverage. Fix: embed the specific historical file content as a literal string (`DAKEFPVF405WING_EDITED_TARGET_C`, pulled verbatim via `git show <last-commit-before-removal>:<path>` in the target repo, not hand-reconstructed) instead of reading live disk state -- matches the pattern the sibling `DAKEFPVF405WING_ORIGINAL_TARGET_C` constant already used. Lesson: any self-test reference point that needs a SPECIFIC historical file's content should embed it as a literal, never read it from a real target directory that upstream can rename/restructure/delete without warning.
- **A same-(tim,ch)-twice hit in `classify_collisions.py`/`simulate_pwm_roles.py` output is NOT automatically a benign parser-gap artifact -- verify which case it is before dismissing it**: the established pattern (identical labels, `#ifdef`-flattened build variant) is real and common, but two counter-examples turned up in one pass (`investigate-shared-tim-dma-request-lines` Phase 2 step 3): (1) `AOCODARCF7MINI` had an undocumented `#if defined(AOCODARCF7MINI_V2)` block (not on the then-current 8-target parser-gap list) producing a genuine flattening artifact (`TIM4_CH1` declared once per branch) that needed the same `make_pwm_shadow.sh` per-variant isolation as the known cases -- but the SAME file's `TIM3_CH2`/`TIM2_CH1` hazard was real (confirmed in the isolated base-variant build, just at a different, correct position than the flattened array showed); (2) `MAMBAF405US` had an undocumented `#ifdef MAMBAF405US_I2C` block whose two branches are near-identical, but isolating each with `make_pwm_shadow.sh` revealed the I2C variant is fully clean while the default (non-I2C) variant has a GENUINE, previously-undetected CERTAIN hazard (`TIM1_CH2`/S4_OUT vs `TIM8_CH3`/S1_OUT, both DMA2 Stream2, second-lowest position 3 -- S1_OUT actually dies on a basic quad) plus an independent `SHARED_TIMER_DMA_REQUEST` hazard on the same line -- the conditional compilation was MASKING a real hazard, not just creating a fake one. (3) `FURYF4OSD` had a same-(tim,ch)-twice `TIM2_CH3` hit with NO `#ifdef` at all -- a genuine unconditional source duplicate (two `DEF_TIM(TIM2, CH3, ...)` lines at different pins, both always compiled), which is real and NOTICE-worthy, not a parser artifact. Lesson: grep every candidate target's `target.c` for `#if`/`#ifdef`/`#ifndef` inside `timerHardware[]` before trusting ANY same-(tim,ch) finding, even for targets not on the currently-known parser-gap list -- that list is not guaranteed complete, and the safe/unsafe direction of the artifact (spurious hazard vs. masked real hazard) isn't predictable without isolating each branch via `make_pwm_shadow.sh`.
- **Searching `dmavar` alternatives one flagged channel at a time under-reports which targets are fixable, because "active" doesn't care what stream the active channel itself is using**: patching the 29-target `SHARED_TIMER_DMA_REQUEST` follow-up list (`investigate-shared-tim-dma-request-lines`, 2026-08-23) initially looked like only ~6 of 29 targets had a clean fix, with the rest reporting "no clean alternative" -- because the first attempt tried each flagged channel's alternate `dmavar` in isolation, leaving its still-flagged siblings' presence unchanged. But `is_shared_multichannel_request()`'s `active_siblings` check only asks "is this OTHER channel genuinely driven at all," never "which stream did IT choose" -- so a sibling that's still a real, live motor output keeps polluting the combined line for anyone else on it, REGARDLESS of which DMA stream the sibling's own dmaInit call ends up using. Moving channel A alone can never clear channel B's hazard if B remains on the combined tuple and A remains driven; A and B (and any other flagged siblings on the same combined group) must be searched IN COMBINATION. Retrying with all of a target's flagged siblings searched together (smallest number of channels changed first) raised the fixable count from ~6 to 27 of 29 -- now built into `find_shared_dma_fix.py`. The remaining 2 (`BEEROTORF4`, `DALRCF722DUAL`) are a genuinely different, irreducible case: a channel whose header table lists the SAME physical DMA stream for every option it has (e.g. `TIM8_CH1` = `D(2,2,0),D(2,2,7)`, both DMA2 Stream2) can never move off that stream at all, so if a DIFFERENT channel's only escape route is that same stream number, no combination of dmavar choices can satisfy both -- one of the two outputs must lose a `DMA_STREAM_COLLISION` outright. When forced to choose, prefer keeping the LOWER-position (more likely S1-S4) output clean, since `DMA_STREAM_COLLISION`'s own severity model already means the lower position wins that collision for free -- see `phase1-findings.md`'s "2026-08-23" update for both worked examples, including how `BEEROTORF4` moved from a genuine CERTAIN hazard (position < 4 dead) to NOTICE (only a non-critical position dies) as a directly measurable improvement.
- **On STM32F4 a wrong `DEF_TIM(tim, ch, pin)` triple COMPILES CLEANLY and silently kills the output -- 9 real instances were sitting in the tree undetected**: `timer_def_stm32f4xx.h:25` expands the pin's alternate-function number from the TIMER NAME alone (`GPIO_AF_ ## tim`; `GPIO_AF_TIM1`=1, `GPIO_AF_TIM8`=3, `GPIO_AF_TIM12`=9), with no per-pin table and therefore no cross-check that the named (timer, channel) is routable to the named pad. F7/H7/AT32 all use per-pin `DEF_TIM_AF__P<pin>__TCH_<TIM>_<CH>` macro tables, so the same mistake is a build error there -- F4 is uniquely exposed, and F4 is also the largest target family (119 F405 + 17 F411 + 1 F427). A first full-tree audit (`check_timer_pin_af.py`, written for this) found **9 findings across 90 F405 targets, zero on the 90 F7/AT32 ones**: `ALIENFLIGHTF4` PB15 declared `TIM1_CH3` where the pad only carries `TIM1_CH3N` (the LED strip pin -- CCxE gets enabled instead of CCxNE, so the WS2811 output never drives); `BLUEJAYF4` and `FF_PIKOF4` each declare PB0/PB1 as `TIM3_CH4`/`TIM3_CH3` with the channels SWAPPED (datasheet: PB0=TIM3_CH3, PB1=TIM3_CH4); `FLYCOLORF4` PB14 as `TIM1_CH3` (pad has `TIM1_CH2N`); `HAKRCF405D` PB8 as `TIM4_CH1` (pad has `TIM4_CH3`); `KROOZX` PB14/PB15 as `TIM4_CH1`/`TIM4_CH2` when TIM4 does not reach those pads at all. Two lessons generalize: (1) never infer pin capability from how another target uses the pin -- "F4" pools F405/F411/F446 with genuinely different AF tables, and an existing target's usage may itself be one of these bugs; the indexed datasheet TSV is the only authority; (2) a `CHx` vs `CHxN` mixup is invisible to every DMA check in this script family, because `timer_def.h` aliases `BTCH_TIMn_CHmN` to `BTCH_TIMn_CHm` -- the DMA analysis comes back perfectly clean on a pad that can never drive.
- **`SILENT_DEAD_MOTOR` is often fixable by remapping the pin to a different timer -- nobody had ever checked, because the only fix-finder searched dmavars**: `find_shared_dma_fix.py` searches `dmavar` reassignments, which is structurally useless for `SILENT_DEAD_MOTOR` (that hazard means the (timer,channel) has NO DMA option list at all -- `TIM9`/`TIM10`/`TIM11`/`TIM12` and `TIM4_CH4` are all `NONE` in `timer_def_stm32f4xx.h`), so these were written off as "dead, nothing to do". But most pads reach several timers and the alternates usually DO have DMA: on F405, PB14 is `TIM12_CH1` (no DMA) but also `TIM1_CH2N` and `TIM8_CH2N`; PA3 is `TIM9_CH2` (no DMA) but also `TIM2_CH4` and `TIM5_CH4`. Of the 6 non-conditional targets with a position<4 dead output, 4 are cleanly fixable (`FISHDRONEF4`, `SPARKY2`, `BLUEJAYF4`, `COLIBRI`). The genuinely-stuck ones share one cause: **F405 PB9 has only `TIM4_CH4` and `TIM11_CH1`, and BOTH are DMA-less** -- that single pin accounts for `ALIENFLIGHTF4`, `FF_F35_LIGHTNING`, `ANYFCF7`, `CORVON405V2`, `KROOZX`, `MICOAIR405MINI`, `MICOAIR405V2`. For those the only mitigation is reordering `timerHardware[]` so the dead pad falls outside S1-S4, which renumbers the outputs and is a documentation-affecting decision, not a silent fix. Now automated as `find_dead_motor_fix.py`.
- **Two traps when evaluating a pin remap, both of which make a broken change look clean**: (1) **the compare-register duplicate.** On a board already driving `TIM8_CH2` on PC7, remapping PB14 to `TIM8_CH2N` looks ideal -- real DMA, no collision anywhere in the sweep -- but `CH2N` is the complementary output of the SAME compare register (`timer_def.h`: `#define BTCH_TIM1_CH2N BTCH_TIM1_CH2`), so the two pads can only mirror each other and the second output becomes unusable for EVERY protocol, strictly worse than merely losing DSHOT. Every DMA check stays silent whenever the two entries pick different dmavars (different streams => no `DMA_STREAM_COLLISION`). `simulate_pwm_roles.py` now emits a `TIMER_CHANNEL_DUPLICATE` hazard for this, keyed on the de-N'd channel; `classify_collisions.py`'s `timer_channel_duplicates()` was keyed on the RAW channel token and so could never catch a base-vs-N pair at all -- also fixed. (2) **the LED-strip timer lock.** `checkPwmTimerConflicts()` excludes every channel of a timer that has a `TIM_USE_LED` entry whenever LED strip is active, so remapping a pin ONTO that timer doesn't produce a working output, it deletes the output entirely. On `FISHDRONEF4` this is what rules out moving PC6/PC7/PC8 to TIM3 to free up TIM8 channels, and it is why that board can only ever recover one of its two dead pads.
- **A hazard-check false positive can land squarely on the fix for a real hazard, so verify a "new" hazard before abandoning a candidate**: `is_shared_multichannel_request()` excluded the entry's own channel from the sibling set by comparing the RAW channel token against the header table's keys -- but the table is keyed on BASE channels only (`_lookup()` de-Ns before lookup) and `active_ch_by_tim` is de-N'd too, so for any N-channel entry `'CH2N' != 'CH2'` meant the entry matched ITSELF and every lone N-channel on a combined request line was reported as `SHARED_TIMER_DMA_REQUEST`. That is not an academic edge case: `TIM1_CH2N`/`TIM1_CH3N` on PB14/PB15 is the standard F405 escape route off DMA-less TIM12, so the bogus flag appeared on exactly the change that fixes a real `SILENT_DEAD_MOTOR`, and made a correct fix look like a regression. Fixed (de-N before the exclusion) with four regression cases in `--selftest` covering both directions -- SOLO N-channel must NOT flag, N-channel with a genuinely driven sibling must STILL flag.
- **When printing a suggested `DEF_TIM` line, match parentheses -- do not regex the arguments**: target.c lines routinely carry trailing comments containing their own parens and digits (`// S5 D(2,4,7)` on MATEKF405SE), and a greedy `.*` argument pattern happily rewrites a digit INSIDE THE COMMENT rather than the real `dmavar` argument -- emitting a "suggested fix" byte-identical to the original except for a corrupted comment. Caught only because the printed dmavar didn't match the dmavar the tool said it had chosen. `find_dead_motor_fix.py`'s `_def_tim_span()` counts parens from the `DEF_TIM(` opener instead, then splits arguments on top-level commas.
- **MATEKF405SE's S5 comment documents a dmavar the code doesn't use**: `DEF_TIM(TIM8, CH3, PC8, ..., 1, 0), // S5 D(2,4,7)` -- `D(2,4,7)` is `TIM8_CH3` dmavar **1**; dmavar 0 is `D(2,2,0)`. A `// D(x,y,z)` comment next to a `DEF_TIM` is a statement of intent that can be independently checked against the header option list, and here it disagrees with the code. Worth spot-checking whenever a target's DMA behaviour doesn't match its comments.
