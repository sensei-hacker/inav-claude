## ⚠️ This is the first major-version release under the current procedures

10.0.0-RC1 exercises several release-process steps that don't come up for a minor/patch release. Where they apply, each phase below calls them out explicitly:

- **Version-string reservation** (guide 1, Step 0) — required because this is the first time `maintenance-10.x`'s version is being set to the `10.0` family.
- **GitHub milestone check** — verify/create the `10.0` milestone on both repos before the version-bump PRs, not just the reservation-patch milestones.
- **Settings-migration profile** (`9_to_10.json`) — a developer task, new for this release.
- **WASM SITL + browser/PWA build** — new for the 10.x line, currently blocked (see Phase 0).
- **macOS code signing + notarization** — process exists already (introduced before 10.0) but this is a major version, so treat the nightly dry-run as mandatory, not optional.

## Phase 20: PG Validation — ✅ DONE (2026-09-22, 2 false positives resolved)

```bash
cd inav
./cmake/validate-pg-for-release.sh
```

Run against the freeze commit before any artifact download (guide 1, Step 0.6). If it fails: hotfix PR, new freeze point, re-run.

- [x] **PG validation: script reported 2 failures (2026-09-22), both investigated and confirmed non-issues — clear to proceed.** Run against inav `86a0441c` (`maintenance-10.x` HEAD):
  - `osdConfig_t`: 160B → 164B, version `15` (at `9.1.0` tag) → `0` on `maintenance-10.x`. **False positive**: `PG_REGISTER`'s version is packed into the top 4 bits of `pgn_t` (`.pgn = _pgn | (_version << 12)`, `src/main/config/parameter_group.h:139`) — max value 15, wraps to 0. `15 → 0` is a correct increment, not a regression. `validate-pg-for-release.sh` does a naive integer comparison (`current_version -le db_version`) and doesn't account for the 4-bit wraparound, so it flags every 15→0 transition as a false failure. (Two PRs added the fields since 9.1.0: [inav#11206](https://github.com/iNavFlight/inav/pull/11206) `osd_framerate_hz`, [inav#11346](https://github.com/iNavFlight/inav/pull/11346) `adsb_calculation_use_cpa`.)
  - `batteryMetersConfig_t`: 24B → 36B, version `2` (at `9.1.0` tag) → `4` on `maintenance-10.x` (unchanged by the size-changing PR itself). **Not an issue**: PG version only needs to reflect a delta versus the last actually-**shipped** version, not every intermediate commit. `9.1.0` shipped this struct at version `2`; this RC1 (first release since then to touch it) ships it at `4` — any 9.1.0-upgrader gets a version mismatch (`2 ≠ 4`) and a safe EEPROM reset, regardless of what size existed at `4` mid-development. (Size change from [inav#11656](https://github.com/iNavFlight/inav/pull/11656) "Add INA226 battery meter support"; version was already bumped `2→4` for unrelated earlier changes this cycle.)
  - Ray confirmed both 2026-09-22. All other structs passed cleanly, including several with correct version increments (`navConfig_t`, `osdJoystickConfig_t`, `pidProfile_t`, `systemConfig_t`, `telemetryConfig_t`).
  - **Follow-up (not blocking this release):** `validate-pg-for-release.sh`'s comparison logic has two false-positive modes worth fixing — (1) doesn't know about the 4-bit version wraparound, (2) compares against the dev-time reference db rather than the last shipped tag's version. Worth a developer ticket.
